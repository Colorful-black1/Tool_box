# Claude Desktop 无感后台同步可行性

日期：2026-10-26。用户明确不接受「点一次打开 Desktop」作为同步，选择继续评估后台机制。本轮只读评估，不实施 IPC 扩展、后台写入、注入、深链调用或真实模型任务。

## 结论

截至当前证据，**尚未找到同时满足“不启动／切到 Desktop、不额外点击、Desktop 开着也能自动出现并继续同一会话”的可靠接入路径**。不应以改按钮、最小化／隐藏窗口或重复导入声称已经实现。

技术上可进一步验证一个较窄的实验方向：**Desktop 完全退出时，只为工具箱拥有的新会话登记记录，下次用户打开 Desktop 时可见**。它依赖未公开的私有存储格式，目前没有在隔离 Desktop profile 中验证；不是已经可交付的功能，也不覆盖 Desktop 正在运行时即时显示。

| 路线 | 是否符合用户目标 | 当前证据和限制 |
| --- | --- | --- |
| SDK 继续写原生日志 | 不足 | 原生日志已有，但 Desktop 有独立列表；本机工具箱自建会话缺少 Desktop 列表记录，用户已验证不可见 |
| 官方 CLI `/desktop`／`--desktop --resume` | 不符合 | 打开 Desktop；官方还列有订阅登录与平台限制，不能代替 CC Switch 第三方场景验证 |
| `claude://resume?session=<id>` | 不符合 | 本机实现执行导入并导航 Desktop，没有在已检查路由中发现静默参数；不是稳定公开的后台登记 API |
| 隐藏窗口启动、导入后切回／最小化 | 不符合 | 仍启动应用、改变应用状态，无法保证无闪烁或不抢焦点，不采用 |
| Desktop 退出时写私有记录，下次启动读取 | 待验证的受限方向 | 启动加载确实读取本机记录；最小记录、索引一致性、归属和重复处理未做隔离验证，不能承诺成功 |
| Desktop 运行时外部写记录 | 证据不足，不能交付 | 当前会话表在进程内维护；落盘文件不等于内存登记或界面刷新。还需解决并发保存、归档、删除与租约竞态 |
| 调用内部 renderer IPC／注入／修改安装包 | 不作为产品路线 | 进程内方法不是对外 API；会绑定内部协议与版本，改变原应用信任边界，用户也未授权此类实施 |

## 核实方式与证据边界

1. 官方 [Desktop 文档](https://code.claude.com/docs/en/desktop#coming-from-the-cli) 说明两端分别维护列表，支持在 Desktop 中使用 `/resume` 选择本机 CLI 会话，继续同一会话；CLI 迁移命令会打开 Desktop，并列有订阅登录条件。
2. 官方 [深链帮助](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link) 描述的是启动／导航／预填，未提供静默后台会话登记接口。没有文档不等于技术上绝对不存在，因此结论是“尚未找到可靠入口”，而非宣称永远不可能。
3. 对本机 Desktop MSIX `3.6556.2.0` 的安装包只读静态检查：
   - 深链 Resume 路由调用 `importCliSession` 后执行界面导航；在已检查的处理代码中没有 `background`／`silent`／`focus` 查询参数分支。
   - `adoptCliSession` 校验／初始化 account、org，检查会话归属和原生日志，更新进程内 session 集合，随后发出 `sessionShown` 并维护持久化／原生日志关联；不是单独复制一段正文。
   - `loadSessionRecords` 在加载存储时读取账户范围内 `local_*.json`，还读取归档等辅助信息，再构造会话状态。发现此路径只能支持“离线登记值得验证”，不能证明任意拼一个 JSON 就能正确出现。
   - `scanRecoverableCliSessions`、`recoverCliSessions` 等内部函数存在，但函数存在不等于工具箱可从外部、安全地无界面调用。没有找到已公开、可复用的后台登记协议。
4. 本轮不读取／输出用户聊天正文、标题、实际项目路径、账号标识或凭据；不调用内部鉴权端点，不启动调试端口，不写安装包或外部数据目录。

以上是指定版本的静态证据。没有运行深链、生成模型任务、创建 Desktop 测试记录或验证 UI 热重载，不能称作端到端验证通过。

## 离线实验若继续，需要先解决什么

此节是实验设计，不是实施授权，也不是承诺完整后台同步：

- 明确只承诺 Desktop 退出后的待登记，随后启动可见；Desktop 运行时排队，不能一边写入一边宣称已同步。进程不存在的快照不能作为跨应用锁，须处理检查后 Desktop 又启动的竞态。
- 先在独立 profile 中验证最小记录与关联索引，不用真实用户会话试错。检查可见、同一 CLI ID、正文完整、重复运行不重复、后续 Desktop／SDK 续接以及退出后不丢失，再讨论正式开关。
- 只处理工具箱来源索引中明确拥有且任务已结束的会话，不能把所有 CLI 日志混入 Desktop，不能自动登记未知结果、归档、删除或其他账号的历史。
- 必须确定 profile、account、org 的归属。多个命名空间、旧 profile、迁移目录或状态不一致时不能猜测“最近一个目录”作为目标。
- 原子创建且不覆盖 Desktop 已有记录，维护最小权限与受控路径；遇到新格式或已有冲突立即停止。仅保留新建自有记录的变更清单，不以批量删除或覆盖用户数据回滚。
- Desktop 的会话列表、原生日志、归档提示和进行中会话有各自状态；需要验证哪些文件是必要关联，不能复制原会话权限、hooks、MCP、临时执行状态、工作树归属或账号认证。
- Desktop 升级后需要版本／格式识别与降级。若需频繁追随私有字段才能保持可见性，应停止该路线；这不符合用户“工具箱应更方便，不增加麻烦”的要求。

在这些验证完成前，不建议为正式功能增加外部写入。本轮保留已有单向发现与原生 ID 续接能力，不新增“已后台同步”状态。
